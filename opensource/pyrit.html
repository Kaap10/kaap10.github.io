microsoft/PyRIT

Greedy Coordinate Gradient (GCG) Adversarial Jailbreak Optimization Engine

Refactored the core Greedy Coordinate Gradient (GCG) adversarial jailbreak optimization engine in Microsoft's open-source AI Red Teaming framework into typed, deterministic, and memory-bounded components.

Key Engineering Deliverables
  • •Phase 1: Candidate Proposal Phase (PR #2671 · Commit d620b4d4): Extracted GCGCandidateProposer with immutable CandidateProposalBatch, preserving shape-grouping invariants, worker ordering, and cross-device gradient tensor migration.
  • •Phase 2: VRAM-Bounded Evaluation Phase (PR #2700 · Commit 132d1cd7): Engineered prompt-level tensor cleanup (del logits, ids) and sequential candidate evaluation loops to strictly eliminate GPU Out-Of-Memory spikes.
  • •Phase 3: Progressive Schedule Controller (PR #2720 · Commit dfa2b763): Modeled state transitions and control-weight ratcheting with ScheduleTransitionAction, guarding against exact-budget boundary edge cases and dangling inf loss resets.

Phase 1: Extract Candidate Proposal Phase (GCGCandidateProposer)

GCGMultiPromptAttack.step() had a monolithic loop that tightly coupled gradient dispatch, per-worker L2 gradient normalization, incompatible tensor shape grouping, token sampling, candidate filtering, and device transfers. This made candidate generation untestable in isolation and prone to subtle regressions.

Phase 2: Extract VRAM-Bounded Candidate Evaluation Phase (GCGCandidateEvaluator)

The logits evaluation and loss accumulation phase was intertwined with attack orchestration. When evaluating thousands of candidate tokens across multiple models and prompts, GPU memory (VRAM) spikes could easily lead to Out-Of-Memory (OOM) errors without timely tensor cleanup.
